## 3. Why every PnL / trade metric is zero

`replay_summary.json` for the run:

```json
{
  "by_strategy": {},
  "runtime_seconds": 30.817,
  "tick_count": 27766,
  "session_id": "2026-05-05T12-50-04Z"
}
```

Diagnostic against the captured book_feed:

```
total slugs: 144
yes books: with_bids=1   with_asks=2   with_both=1
no books:  with_bids=2   with_asks=1   with_both=1
```

Of 144 captured markets, only **1 slug** has a YES book with both bids
and asks populated. Most snapshots are one-sided: YES carries only
bids, NO carries only asks. The walked-VWAP entry gate (and the new
realistic-fills wrapper in `PaperTrader`) require both sides on the
side they walk — `yes.asks` for an Up entry, `no.asks` for Down. With
the captured data, almost every entry rejects as `empty_book` or
`paper_no_fill`.

This is the **scraper bug** described in `MEMORY.md`:

> "every scraped snapshot in book_feed/ has empty bids/asks despite
> REST /book showing real liquidity; preexisting, deferred from
> walked-VWAP work"

The live daemon at the time of the capture saw both sides via its
WebSocket subscription and traded normally (63 walked_vwap entries
+ 121 refined entries logged in `events.jsonl`). The scraper that
produced `book_feed/` only persisted one side per token — that's
the data on disk that replay reads.
